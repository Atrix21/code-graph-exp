# Experiment 2: decision log

- **E2-D01** · Two protocols. *Agentic* (primary): a coding agent explores with tools. *Single-shot* (secondary): a model gets one method's retrieved context. · Agentic answers "does it help an agent"; single-shot isolates the value of the context itself and is cheap. · Single-shot only (wouldn't measure tool-use efficiency).
- **E2-D02** · The agent is Claude Code headless (`claude -p`), not a custom loop. · It is a real coding agent with native Read/Grep/Glob, so the baseline is how agents actually work today. There is no API key for a custom Messages loop.
- **E2-D03** · Isolation profile `restricted-oauth`: `--restricted`, `--strict-mcp-config`, `--tools Read,Grep,Glob`, `dontAsk`, `--disable-slash-commands`, CLAUDE.md/auto-memory disabled, custom system prompt. · Verified from recorded request bodies. `--bare` offers only Read (and requires an API key). `--safe-mode` drops `--mcp-config` servers.
- **E2-D04** · Zero-cost validation through a local mock of the Messages API (`ANTHROPIC_BASE_URL` + dummy key, so an ignored base URL means a 401, which is not billed). It records exactly what the model would receive and replays scripted tool calls. · The guide-suggested "start then interrupt" check risked partial billing.
- **E2-D05** · Workspaces: a `git archive` export of one single-bug snapshot, re-initialised as a single neutral commit, at `/tmp/work/<HMAC(task)>/app`. Node modules sit above the cwd. · Prevents history, branch and path leakage; CRG needs `.git`.
- **E2-D06** · Competitors through their **native** MCP servers, defaults, read-only. Write- and network-capable tools are denied in every condition (CRG refactor/wiki/embed, Graphify PR tools). · Their intended agent-driven use, which experiment 1 could not test. The tool-count asymmetry is reported, not equalised.
- **E2-D07** · Our methods are exposed as one `search_code` tool (same name, description, 4k budget for hybrid, custom_graph, embeddings and bm25), using the frozen experiment-1 configs. Query embeddings come from a persistent server (cosine ≥ 0.99999 vs experiment 1).
- **E2-D08** · Primary metric RC+line@1 (right function and pointing at the mutated lines ±2, with a range-width cap). Automatic and LLM-free; tested on all 20 tasks. · An LLM judge would add cost and judge bias.
- **E2-D09** · The unit of analysis is the task. Primary analysis on the 14 test tasks with 3 repeats. Confirmatory family H1a, H1b, H1c×2 and H2×2 with Holm correction.
- **E2-D10** · Independent audit before any approval request (READY-WITH-FIXES; 4 blockers, all fixed). Highlights:
  - absolute-path answers scored 0 (would have penalised CRG);
  - no init-fingerprint exclusion;
  - infrastructure errors scored as wrong;
  - no resume or orphan cleanup;
  - mock detection inferred from the environment (gateway bypass).
- **E2-D11** · Explicit billing mode (`subscription` | `api-key`), named in the approval and enforced by the child env, the approval check and the init `apiKeySource`. · The user's subscription hit its weekly limit during development, so API-key billing must be possible, but never by accident.
- **E2-D12** · Privacy fix. The isolation verifier's positive control (deliberately run without isolation) had stored raw request bodies containing the user's CLAUDE.md, memory and email, and the verifier hardcoded the email. Now: needles are read at runtime and reported only as hashes, control recordings are deleted after analysis, and the affected local, unpushed commit was amended and purged. No commit contains the data.
- **E2-D13** · Account binding. Billable subscription runs must name a Claude Code account (`--account`, resolved with `claude-account`); the approval names it and the harness checks the login (`claude auth status`, local) before any run. The primary account (`~/.claude`) runs with `CLAUDE_CONFIG_DIR` unset. Only the account name, plan type and an e-mail hash are recorded. · The owner asked for the "cc personal" profile; several logins exist on this machine.
- **E2-D14** · Strictly sequential execution: one `claude` process at a time (agentic `--parallel 1`, single-shot concurrency 1, one CLI invocation at a time). · The owner's instruction ("one experiment at once, not parallely"). It also keeps usage-limit pressure low and latency measurements uncontended.
- **E2-D15** · Single-shot over Claude Code gets the agentic run discipline: append-only `ss-raw.jsonl` with resume; infrastructure errors and init mismatches are excluded, not scored; the same halt rules; init check (StructuredOutput only); `--effort high` pinned as in the agentic protocol; seeded run order (20261108). · Before this, a usage-limit hit mid-run would have scored the remaining items as wrong answers.
- **E2-D16** · Approval received (2026-11-08): run the experiments on the personal (Pro) subscription, sequentially. Model Sonnet 5.5 (the recommended default; the owner did not name one). Executed stage by stage: stage 1 (smoke pilot) runs first and must pass the first-run checklist (real init fingerprint, parse rate, measured cost) before stages 2 and 3 are added to `APPROVAL.json`.
- **E2-D17** · Stage 1 (smoke pilot, 2 dev tasks; `results/stage1-*`) passed the first-run checklist: 10/10 agentic and 36/36 single-shot runs valid, 0 exclusions, real init fingerprint as expected on every run (OAuth `apiKeySource: none`, only built-in plugins), $1.85 list-price total. **Finding: under p1 the agent never called an attached retrieval tool** (0 calls in 8 MCP-condition runs; Grep + Read solved both tasks in 4–10 turns), so p1 conditions differ only by tool-schema overhead. Added prompt **p2** = p1 + one condition-neutral sentence directing the agent to an MCP search/graph tool when one is attached (a no-op for the baseline). Stage 2 runs p1 (natural tool choice) and p2 (directed) on dev; the main-run design is frozen from the dev data. · p1 alone can only answer "does merely offering the tool help"; p2 measures whether the retrieved content helps once it is used. Both are part of the research question.
- **E2-D18** · Cost reconciliation. Claude Code writes the prompt cache with a 1-hour TTL (billed 2x input) and prices Sonnet 5.5 cache reads at $0.10/M; our list recomputation priced every cache write at 1.25x. Fixed: 1-hour writes at 2x; cache reads stay at the published $0.20/M (so the recomputation is the higher, conservative figure for the ledger). The pre-registered cost metric remains Claude Code's `total_cost_usd`. Cross-run prompt caching (1 h) makes repeated or shared contexts cheaper and faster (e.g. single-shot `none`@8k reused the @2k prefix), so efficiency is reported in tokens as well as cost, and the seeded run order spreads cache warmth across conditions.
- **E2-D19** · Freeze (protocol Amendment A). Main run: agentic p2 and p1 (5 conditions × 14 test tasks × 3 repeats each) and single-shot as pre-registered; confirmatory H1a/H1b/H2 on p2, H1c on single-shot, Holm over the same 6 tests; p1 comparisons secondary. Hashes of the protocol, prompts, scorer, analysis, harness and test contexts in `FROZEN.json`. · Dev data: p1 never exercises the tools, so confirmatory tests on p1 would test only "offering" a tool; p2 tests whether the retrieved content helps once used. Decided on dev only, before any test-split run.
- **E2-D20** · Usage-limit handling (post-freeze harness fix; scoring and analysis untouched). Stage 3 stopped at 22:01 on the plan's 5-hour limit ("You've hit your 5-hour limit · resets 12:30am"), which the limit pattern did not recognise: it was classified `api_error`, retried, and halted only after 3 consecutive errors (68 p2 runs scored by then). Fixed: the pattern covers the subscription messages; a limit halts at once; limit exclusions (including the 3 earlier records, recognised from their text) never count as attempts, so interrupted runs are re-run on resume, not dropped. `run-stage3-loop.sh` resumes automatically after each stated reset; a `STOP` file ends it. · A usage limit is an interruption, not a property of the run; counting it as a failed attempt would silently drop test items.
- **E2-D21** · Main run complete (2026-11-09 10:43): 1,176/1,176 test runs scored; 4 usage-limit interruptions re-run; three 5-hour windows; $33.99 list-price cumulative. Results and interpretation in `findings.md`. All 6 confirmatory tests not supported (agentic accuracy at ceiling; hybrid not cheaper or leaner than baseline; single-shot hybrid > embeddings +0.07/+0.10, n.s.). The stage-3 wrapper first mis-parsed one reset time (read from a file without the message) and was fixed before it could matter beyond an idle wait (f1a80c0).
