Labels. ESTABLISHED = peer-reviewed or replicated, with numbers. ### 1.2 Studies of tool-output verbosity and context growth

- Lost in the Middle (Liu et al., TACL 2024) https://arxiv.org/abs/2307.03172 : accuracy is highest when relevant information is at the start or end of the context and drops when it is in the middle, even for long-context models. ESTABLISHED for the direction; I did not extract effect sizes.
- Context Rot (Chroma, July 2025) https://research.trychroma.com/context-rot , code https://github.com/chroma-core/context-rot : 18 LLMs, performance degrades as input length grows even on simple tasks; the report itself says input length and task complexity are hard to disentangle. REPORTED (technical report, not peer reviewed). Secondary blog figures (20 to 50% drops) I could not verify and exclude.
- The Limits of Long-Context Reasoning in Automated Bug Fixing https://arxiv.org/abs/2602.16069 : in mini-SWE-agent on SWE-bench Verified successful trajectories typically stay under 20k to 30k tokens; with relevant files supplied at 64k single-shot, Qwen3-Coder-30B-A3B resolves 7% and GPT-5-nano 0%. Longer accumulated contexts correlate with lower success. REPORTED.
- The Complexity Trap https://arxiv.org/html/2508.21433v3 : in SWE-agent about 84% of an average turn is observation tokens (preliminary experiment); compares observation masking to LLM summarisation. REPORTED.
- SWE-Pruner https://arxiv.org/pdf/2601.16746v3 : file-inspection commands are about 76% of token cost in mini-SWE-agent / Verified / Claude Sonnet 4.5. REPORTED.
- AgentDiet https://arxiv.org/html/2509.23586v1 : trajectories contain redundant/expired information; inference-time reduction cuts cost without hurting performance. REPORTED.
- SWE-agent ablations above (summarised search +6 points over iterative; 100-line window +5.3 over full file). These are the strongest direct evidence that how much a tool returns matters.

This matches the project's own result that big MCP outputs are re-read every turn and raise total tokens. The literature supports "concise, bounded outputs"; it gives no reason to expect a graph tool to be exempt.

### 1.3 Does ANY published evidence show graph advantage growing with repository size?

I looked specifically for stratification by repository size, number of files, graph size or connectivity in every paper above and ran a dedicated search ("graph-based code retrieval benefit increases with repository size", then SWE-bench Pro/size).

Result: none found.

- RepoGraph, CodexGraph, LocAgent, CoSIL, OrcaLoca, KGCompass, SweRank: aggregate gains only. CoSIL states outright it gives no breakdown by repo or graph size. LocAgent stratifies by hop distance (difficulty), not size.
- Closest evidence (weak, indirect):
  - KGCompass: ground-truth function sits 2 hops from the issue-mentioned entity in 74% of cases (distribution of where answers lie, not a benefit-vs-size curve). REPORTED.
  - LocAgent: `TraverseGraph` ablation costs 2 to 6 points; the lexical entry point matters more. REPORTED.
  - OrcaLoca motivates with "3,010 files / 438k LOC" average SWE-bench repo but does not test size dependence.
  - GraphCoder and CodexGraph report graph *cost* rising with size (retrieval efficiency; Sympy indexing OOM), which is evidence against a free lunch at scale.
  - SWE-bench Goes Live https://arxiv.org/pdf/2505.23419 (as summarised by a search snippet, not read in full): success falls below 10% once a patch edits three or more files or more than 100 lines, and size is "an informative but imperfect proxy" for difficulty. This ties difficulty to patch spread, not to repo size.
  - SWE-bench Pro https://arxiv.org/html/2509.16941v2 (search snippet): reference solutions span about 107 lines in 4.1 files and frontier models score under 25%. No repo-size analysis found.
  - A Medium post ("Hindsight") says graph signals help most on broad/ambiguous queries; it is a blog, query-type not size, SPECULATIVE.
- Conclusion: the scaling hypothesis is untested in the literature, not refuted. Nearly every benchmark is Python and SWE-bench-like, repos are all large relative to our 6k-line repo (SWE-bench average about 3k files) and span a narrow range, so no study had the within-benchmark size variation needed. A design that varies size while holding language, framework and task type roughly fixed would be novel.

### 1.4 Synthesis

Established (replicated or strongly consistent across independent groups):
1. A lexical or semantic entry point is the dominant component of localisation (LocAgent ablation: removing SearchEntity -19 file Acc@5; removing graph traversal -2). Same as our own result that call-graph traversal was the only graph component with a measurable effect, and a small one.
2. Concise, bounded tool outputs beat verbose ones for agents (SWE-agent ACI ablations; observation-dominance studies). Long accumulated context correlates with lower success.
3. Long-context position and length effects are real (Lost in the Middle, peer reviewed).
4. Single-run agent scores are noisy by multiple points (Section 4).

Reported but not independently replicated:
- Graph-guided agents give +2 to +20 points localisation/resolve over non-graph variants, depending on baseline and metric. Typical resolve gains over strong baselines are small (RepoGraph +2 to 2.7 points; CodexGraph ties AutoCodeRover). The larger numbers (KGCompass +20 points) compare to pure-LLM without retrieval, not to a good grep baseline.
- A trained non-graph retriever (SweRank) matches or beats a graph agent on function-level Acc@10, so "graph vs not" is confounded by training.

Not established:
- Whether graph retrieval gain grows, shrinks or is flat as repository size or connectivity increases. No stratified evidence.
- Whether any gain survives a competent grep/glob/read agent (our own prior result says it did not, at 6k lines, 14 tasks, 100% solved).
- Language beyond Python for graph agents (SpIDER is the only one found with TypeScript results).

Strongest evidence FOR the scaling hypothesis: only indirect. The mechanism-level argument that search space grows with repo size (OrcaLoca motivation, 3,010 files avg) plus SpIDER's consistent expansion gains over dense retrieval at fixed budget across languages including TypeScript (https://arxiv.org/abs/2512.16956). Neither is a size-stratified result. SPECULATIVE as a scaling claim.

Strongest evidence AGAINST: (a) CodexGraph and GraphCoder report that graph construction/query cost grows with repo size and verbose graph outputs inflate tokens (102k tokens avg on SWE-bench Lite for CodexGraph); (b) SWE-agent ACI and trajectory studies show verbose tool output lowers success; (c) SweRank shows a non-graph retriever matches a graph agent. None of these refutes growth of the *benefit*, but they predict that graph tools' cost grows alongside any benefit.

## 3. Candidate repositories for scale validation

Priority per coordinator: TypeScript, ideally NestJS, at two scales so the extractor, chunkers and harness are reused unchanged. Go retained as a short secondary section.

### 3.1 How measured

- GitHub languages API (`/repos/{r}/languages`) is repo-wide (includes frontend, docs, tests, generated code), so I did not use it for backend size.
- Backend size = sum of `size` bytes of `.ts/.tsx` blobs under the backend directory from the git trees API (`git/trees/{branch}?recursive=1`), excluding `.d.ts`, test/spec/e2e/mock directories, migrations and `generated` paths. LOC is bytes / 37. Calibration: I fetched 40 immich and 120 twenty-server source files and measured 36.9 and 36.7 bytes per line (pooled). Treat LOC as roughly +/-15%.
- Tree for twentyhq/twenty at repo root was truncated by the API, so I fetched the `packages/twenty-server` subtree separately (not truncated).
- Bug-fix PR counts: GitHub search `is:pr is:merged linked:issue merged:>=2026-06-01`. "linked:issue" captures PRs with closing-keyword links or sidebar links, so it is a proxy for "fixes #N" not "is a bug". I also sampled up to 60 PRs per repo with "fix" in the title (most recent first among linked ones) and fetched their file lists to count how many touch a test file and how many touch both a test and a backend `.ts` file. Samples are small (n=39 to 60) and the filters are heuristic (test path regex, backend path prefix); use as order of magnitude only. (Script and raw output are in the session scratchpad, not in the repo.)
- Date reference: model cutoff mid-2026; "after 2026-06-01" counts are PRs merged in the ~5 months to 2026-11-09.

**MEDIUM target: immich-app/immich `server/` (about 54k non-test LOC).**

**LARGE target: twentyhq/twenty `packages/twenty-server` (about 760k non-test LOC; well above 200k).**

## 4. Methodology for small-n paired evaluation of LLM agents

1. Report standard errors, use paired differences. Miller, "Adding Error Bars to Evals" https://arxiv.org/abs/2411.00640 (Anthropic; arXiv preprint): report SE of the mean; compare two systems with the question-level paired difference ("use the paired version wherever practicable"), because question scores are positively correlated across systems; use clustered SEs when questions are grouped (cluster adjustment up to 3x larger than naive); resample answers per question to cut within-question variance (limit stated for the example: 2/3 reduction); do not lower temperature to reduce variance. Power: n = (z_{a/2} + z_b)^2 * (omega^2 + sigma_A^2/K_A + sigma_B^2/K_B) / delta^2, where omega^2 = Var(x_A) + Var(x_B) - 2 Cov(x_A,x_B). His example needs about 969 questions for delta=0.03, which is far above our n. REPORTED (single widely used preprint).
2. At small n the CLT fails. Bowyer, Aitchison, Ivanova, ICML 2025 https://arxiv.org/abs/2503.01747 : CLT intervals are too narrow when n is below a few hundred (95% nominal had 92.5% coverage at N=100); for one system use Wilson or Beta-Binomial intervals; for clustered questions use a hierarchical Bayesian beta-binomial; for two systems on the same questions use the "paired Bayes" model (all non-Bayesian methods, including CLT on paired differences, severely underperform at small N); Python library https://github.com/sambowyer/bayes_evals . ESTABLISHED (peer reviewed; simulation-based).
3. Repeated runs are mandatory for agents. "On Randomness in Agentic Evals" https://arxiv.org/html/2602.07150v2 : 60,000 SWE-bench Verified trajectories; single-run pass@1 varied 2.2 to 6.0 points across 12 configurations; SD about 1.0 to 1.8 points even at temperature 0; recommends several runs per task; with sigma about 1.5 points, 9 runs per agent for 80% power to detect a 2-point gain, 36 runs for 1 point; report pass@1, pass@k and pass^k. REPORTED (preprint). Older figure for contrast: SWE-agent's six GPT-4 runs had SD about 0.5 points (https://arxiv.org/pdf/2405.15793, via search snippet), so variance depends on model and scaffold.
4. Paired-binary analysis, per task across arms: McNemar / exact conditional binomial test on discordant pairs, or the paired Bayes model above. Power depends on the number of discordant tasks, not the total (standard statistics, derived; no citation needed but flag as SPECULATIVE in the sense of not taken from the literature above). With 14 tasks and 100% success in both arms, there are no discordant pairs, so success rate carries no information; use continuous outcomes (tokens, turns, cost, localisation recall).
5. Slope of benefit vs repo size or connectivity: a mixed-effects (hierarchical) model with task as random effect nested in repo and arm x log(size) interaction; with only 2 to 3 repos the repo-level slope has 0 to 1 degrees of freedom, so size is confounded with repo identity. This is standard hierarchical-modelling practice; I did not find a paper that applies it to agent evals, so treat the recommendation as SPECULATIVE. Practical response: report the slope as descriptive, add multiple size points (subsystem subsets of one repo at several scales, i.e. within-repo size manipulation by restricting the searchable corpus), and use a task-level cluster bootstrap or Bayesian hierarchical model with a weakly informative prior.
6. Contamination control: prefer post-cutoff tasks (SWE-Bench Illusion https://arxiv.org/abs/2506.12286 : up to 76% buggy-file accuracy from issue text alone, 53% on non-benchmark repos).

## Implications for our design

Supported by the literature:
1. Keep tool outputs small and bounded (window/budget) in every arm; SWE-agent's ablations (100-line window +5.3 points vs full file; summarised search +6 vs iterative) and the observation-token studies make verbose outputs a confound to be controlled, not a property to attribute to "graph".
2. Include a strong lexical entry-point baseline; in LocAgent the lexical entity search ablation mattered ten times more than graph traversal (-19 vs -2 points file Acc@5), and our own result agrees.
3. Include a non-graph trained or embedding retriever arm when feasible; SweRank shows it can match a graph agent, so "graph vs grep" alone overstates the contribution of the graph.
4. Use paired per-task analysis with clustered or Bayesian intervals (Miller; Bowyer); with n in the tens, normal-approximation error bars are too narrow.
5. Run each task/arm multiple times (about 3 to 5 minimum, more if budget allows) and report pass@1 plus spread; single-run differences of 2 to 6 points are noise-level.
6. Use post-2026-06-01 fixes for task mining and verify FAIL_TO_PASS locally; no benchmark covers these repos, and memorisation of popular repos is documented.
7. Expect no help from published stratified results; none of the 12 graph-retrieval works I read reports benefit by repo size, so any scale curve we produce is new evidence, not a replication.

Our hypotheses (not supported by the literature):
8. Benefit of graph retrieval grows with codebase size and connectivity (graph-guided agents' gains over grep in a 6k-line repo were zero; whether they appear at 54k and 760k LOC is untested anywhere).
9. NestJS DI/module structure makes graph edges more informative than plain call edges at scale; this is a reason to choose immich (Nest, Kysely) and twenty (Nest, TypeORM), but the effect of DI edges has no published test.
10. Size and architecture differ between immich and twenty, so a 2-point ladder confounds them; add a within-repo size manipulation (restrict corpus to subsystems of twenty-server at about 50k, 150k, 400k, 760k LOC) to separate size from architecture.
11. Success-rate ceilings (100% solved at 6k LOC) will likely shrink at 54k and 760k, which is what creates room for a benefit; confirm with a no-retrieval pilot arm before spending budget, and prefer secondary outcomes (tokens, turns, localisation recall) if success stays saturated.
12. Practical risks to resolve first: ts.Program load of twenty-server, TS 6 compatibility on immich, AGPL/enterprise file handling for twenty, and whether at least 30 usable post-cutoff tasks per repo survive filtering.
