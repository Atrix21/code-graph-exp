## 1.6 Why the indirect boundaries are hard for grep

1. Job producer and consumer share only a string-valued enum member. `jobRepository.queue({ name: JobName.AssetGenerateThumbnails })` (`job.service.ts:119`) has no call edge to `MediaService.handleGenerateThumbnails`; the link is the decorator argument at `media.service.ts:191`, resolved at runtime into a map (`job.repository.ts:66`). Grepping the enum name returns producers, the decorator, the type union entry (`types.ts`), `enum.ts`, specs, and the QueueAll variants (`...QueueAll` names also match substrings of the single-asset name).
2. The queue is chosen only by the consumer's decorator (`getQueueName`, `job.repository.ts:193`); a producer never states it.
3. "What runs next" is not in the handler. The follow-up for a finished job lives in a different class's switch (`JobService.onDone`), keyed on `item.name` and on payload fields such as `source === 'upload'` (`job.service.ts:118,166,250`). The handler returns only `JobStatus`. To learn that storage-template migration triggers thumbnail generation you must read `job.service.ts`, not `storage-template.service.ts`.
4. Event names are string literals typed by one map (`event.repository.ts:24-113`); emitters and listeners are connected by reflection at startup (`:170-219`). One emit can have several listeners in unrelated services (`AssetCreate`: workflow + quota; `AssetMetadataExtracted`: storage template + notification + workflow), and listener order depends on `priority` and the `workers` filter.
5. Cross-process relay is two-step and implicit: `ConfigUpdate` is emitted by `SystemConfigService` (`system-config.service.ts:101`) but the microservices worker receives it only because `NotificationService.onConfigUpdate` forwards it through socket.io/Redis (`notification.service.ts:114`) and `WebsocketRepository.afterInit` re-emits it (`websocket.repository.ts:80-84`). Nothing in the config service mentions the other process.
6. Dependency injection by property name: all 56 repositories are inherited fields (`base.service.ts`), so `this.x.method()` call sites do not import the repository, and many repositories expose same-named methods (`get`, `create`, `getById`, `update`), so grep on a method name is ambiguous across ~66 repositories.
7. Same class, different behaviour per worker: `@OnEvent({ workers: [...] })` and the `ImmichWorker` switch inside handlers (`queue.service.ts:46,68,85-88`) mean a single method body serves different roles in API vs microservices.
8. The ML boundary is an HTTP contract with a different-language service; the request is assembled from `ModelTask`/`ModelType` enums (`machine-learning.repository.ts:190-225`) and the receiving code is not in `server/`.
9. Duplicate textual copies: `queries/*.sql` repeat every `@GenerateSql` query, the OpenAPI/generated artefacts repeat DTO names, and ~109 spec files repeat symbol names, so symbol grep returns many non-implementation hits.

# Section 2. Historical bug mining

## 2.1 Method

- Source of truth: git history of `origin/main` in `targets/exp3/immich-history` (squash-merge commits, subject ends in `(#PR)`), PR/issue text via `gh pr view` / `gh issue view` (read-only). I used `git log --since=2026-06-01 -- server/src server/test` rather than `gh pr list --search` because GitHub search tokenises titles loosely; counts from both are given.
- Pool definition: commit subject starts with `fix` or `revert` (any scope) AND the commit changes at least one non-spec file under `server/src`.
- Counts. GitHub search `fix(server) in:title` merged-PR totals: **113 merged after 2026-06-01**, **715 merged on/before 2026-06-01** (UNVERIFIED that every hit is a `fix(server)` title, search is fuzzy; 101 of the 262 PRs returned by a looser search start with `fix(server`). Git pool as defined above: **163 commits after 2026-06-01** (107 with a spec/medium test changed), **795 on/before 2026-06-01** (315 with tests; by year 2022: 9, 2023: 160, 2024: 283, 2025: 229, 2026 before June: 114). Only the 163 post-cutoff commits were mined; **accepted candidates before the cutoff: 0 by design, after: 98**. Fixes labelled `feat`/`chore`/`refactor` that are really bug fixes are not in the pool (known gap).
- `fixed_functions`: for each changed non-test `.ts/.tsx` file, hunks of `git diff -U0 parent..merge` are mapped on the OLD side to the innermost named function/method/arrow-in-variable using the TypeScript AST of the parent version (`Class.method`; `module-level` when none; `[property]`, `[insertion...]` annotate special cases; new files appear as `(new file)`).
